# Ken — Internationalization (i18n)

Ken's **human web UI** is multilingual. It resolves a language per request and
translates every page through a **reloadable message catalog**. English,
Spanish, and French ship embedded; you can **add a language, or override any single string,
at runtime — no recompile, no restart.**

**Scope.** This covers the human-facing web UI only. The **AI/MCP surface**
(tool schemas, server-delivered instructions, `kb_*` responses) and the **server
logs** are intentionally English-only — they are a machine/operator contract, not
end-user copy.

---

## For operators & translators

### Where translations live

At startup Ken reads an external i18n directory:

- `KEN_I18N_DIR` if set, otherwise **`<data-dir>/i18n`** (the `i18n` folder next to
  your database file — e.g. `/var/lib/ken/i18n` when the DB is `/var/lib/ken/ken.db`).

Files there **override and extend** the embedded English, Spanish and French defaults. The
directory is optional: with nothing dropped in, Ken runs on the embedded catalogs.

### File naming

| File | Language |
|------|----------|
| `messages.properties` | English — the default. Its `settings.field.*` entries are **GENERATED** from the Go registry; see below. |
| `messages_es.properties` | Spanish |
| `messages_<lang>.properties` | any language, by its code (`fr`, `de`, `pt-br`, …) |

The `<lang>` code is whatever you name the file; each file declares its own display
name (endonym) for the language selector via the `lang.self_name` key.

### File format

UTF-8 Java-style `.properties`:

```properties
# Comments start with # or !  (blank lines ignored)
lang.self_name = Français
nav.search     = Rechercher
# {0}, {1}, … are positional placeholders filled in at render time
browse.page    = Page {0}
```

- The **first** `=` or `:` on a line separates key from value, so a value may
  contain `=` freely (e.g. `… blocked (0 = never block).`).
- Escapes: `\n`, `\t`, `\\`, `\uXXXX`. A leading UTF-8 BOM is ignored.
- Keys are dotted names (`nav.search`, `entry.promote`); they are opaque strings,
  not a hierarchy.

### The two things you can do

1. **Override a few strings** (keep the current language, change some wording).
   Drop a file containing **only the keys you want to change** — every other key
   falls back to the embedded default. Example — soften one label in English by
   creating `messages.properties` with just:

   ```properties
   login.lede = Curator sign-in. Agents use tokens, not this form.
   ```

2. **Add a whole language.** Copy the English `messages.properties` (the canonical
   key list — it lives in the repo at `internal/i18n/locales/messages.properties`,
   or model your file on the shipped `messages_es.properties`), rename it
   `messages_<lang>.properties`, set `lang.self_name`, and translate the values.
   Anything you leave out falls back to English, so a **partial** translation is
   valid and improves as you fill it in.

   If you translate any `settings.field.*` entry, give it a `#@src` stamp — see
   **Settings text** below. An unstamped one is reported as unverified, because
   "nobody recorded what this was translated from" and "this is stale" are the same
   actionable state.

### Reload — live, no restart

Ken re-reads the external directory when its files change (checked at most every
couple of seconds). Save your file, reload the page, and the new text appears.
Bad or missing files are skipped, never fatal.

### Choosing the language

- A **language selector** in the top bar lists every language present (English
  first). Selecting one sets a `ken_lang` cookie.
- With no cookie, Ken honors the browser's `Accept-Language` when it matches an
  available language.
- Otherwise it falls back to English.

### Fallback chain

For every key, in order: **selected language → English → the key name itself.**
You therefore never get a blank string; an untranslated key shows the English
value, and a genuinely unknown key shows its name (a visible signal to fix it).

## Specifics worth knowing

### Plurals

Count-sensitive strings use paired `.one` / `.other` keys, and `{0}` defaults to
the count:

```properties
nav.proposals_pending.one   = {0} pending
nav.proposals_pending.other = {0} pending
dashboard.cta_waiting.one   = {0} proposal is waiting for review.
dashboard.cta_waiting.other = {0} proposals are waiting for review.
```

`.one` is used when the count is exactly 1, `.other` otherwise. Languages whose
plural rules need more forms can express them with their own paired keys. (English
and Spanish use the one/other split — which is why "1 proposal is waiting" reads
correctly instead of "1 proposals".)

### Domain enum values (kind, state, staleness, …)

Controlled-vocabulary values shown as badges/labels — an entry's *kind*
(`reference`, `feedback`, …), a revision's *state* (`proposed`, `curated`, …),
*staleness*, *lifecycle*, the activity-feed *event*, the browse *sort*, and an
agent's *kind* (`ai`/`human`) — are translated for display under
`enum.<class>.<value>` keys:

```properties
enum.state.proposed = propuesta
enum.staleness.stale = obsoleta
enum.kind.reference  = referencia
```

English values are identity (so the English UI is unchanged), Spanish is
translated, and **a missing key falls back to the raw value** — so a brand-new
enum value shows verbatim, never as a key. The raw value is still used internally
for CSS state hooks, `<option>` values and query filters; only the visible label
is translated.

### Settings page fields

The `/settings` field **labels, help text, and group names** are translatable too,
keyed by the field's stable id and the group slug:

```properties
settings.group.rate_limiting        = Rate limiting
settings.field.rl_ip_rpm.label      = Per-IP requests / minute
settings.field.rl_ip_rpm.help       = Sustained per-IP request rate.
```

**The bundle WINS over the Go registry — it is an override, not a mirror.** That
asymmetry caused a real defect: release 1.6.0 renamed settings and rewrote their help
in `internal/settings/settings.go`, nobody touched the bundles, and the console went
on rendering the old names and the old *semantics* — one entry told operators in three
languages that message bodies are destroyed at acknowledgement, months after that
stopped being true. The fields **added** in the same release rendered correctly,
precisely because nobody had translated them yet.

So the two halves are handled differently, and neither is edited by hand:

- **English is GENERATED.** Do not edit `settings.field.*` in `messages.properties`.
  Change the label or help in `internal/settings/settings.go`, then run:

  ```
  go run ./internal/i18n/i18nsync
  ```

  A test regenerates the block in memory and diffs, so English drift cannot be merged.

- **Other languages carry a `#@src` fingerprint** of the English they were translated
  from, on the comment line directly above each entry. When the registry text changes
  the fingerprint stops matching and the test fails, naming the key, the language and
  both English texts. Nothing else can detect this: a translation is *supposed* to
  differ from its source, so no string comparison can tell a good one from a stale one.

  After correcting a translation, stamp it — one key at a time, on purpose:

  ```
  go run ./internal/i18n/i18nsync -stamp es -key settings.field.comm_message_ttl_sec.help
  ```

  There is deliberately **no bulk stamp**. A stamp claims somebody read the new English
  and confirmed this translation still says it; a `-stamp-all` flag would make that
  claim about every string at once, and the first person facing a wall of failures
  would reach for it.

*(Runtime validation errors name their fields through the bundle, so they match the
form. Their reason text is still English — that is a known gap, not a design.)*

## For developers

- Package: `internal/i18n`. Embedded defaults: `internal/i18n/locales/*.properties`.
- Templates call view methods, not the manager directly:
  - `{{.T "some.key"}}` — translate; `{{.T "some.key" arg0 arg1}}` fills `{0}`, `{1}`.
  - `{{.TN "some.key" .Count}}` — plural; resolves `some.key.one`/`.other`, `{0}` = count.
- **Adding a key:** add it to `messages.properties` (the source of truth) **and** to
  `messages_es.properties`, then reference it from the template. Keep the two files
  in sync; a key present only in English still renders (via fallback) but shows
  English under Spanish.
- **The English `.properties` is authoritative for the key set.** Do not hardcode
  user-facing strings in templates or handlers — route them through a key so they
  stay translatable and reloadable.

## Verifying it works

1. Point at a scratch data dir and create the i18n folder:
   `mkdir -p "$KEN_DATA/i18n"`.
2. Drop `messages_fr.properties` with at least
   `lang.self_name = Français` and one real key (`nav.search = Rechercher`).
3. Reload any page → **Français** appears in the language selector; pick it and the
   translated key shows, everything else falls back to English.
4. Edit the value, save, reload → the change appears within a couple of seconds
   (no restart).
5. Delete the file, reload → the language disappears from the selector.
