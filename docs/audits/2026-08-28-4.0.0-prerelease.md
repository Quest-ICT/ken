## Verdict

# KEN 4.0.0 — PRE-RELEASE AUDIT VERDICT

**Not safe to tag as it stands.** Nothing found loses data, corrupts a database, or opens a security hole, and the schema half of the release is verified sound (a real in-place 24→26 / 19→20 upgrade with hand-seeded awkward rows: `integrity_check` ok, `foreign_key_check` empty on both databases, all rows preserved, and the upgraded `sqlite_master` byte-identical to a fresh 4.0.0 install). What fails is (a) two live-behaviour regressions this wave introduced, and (b) the release's own stated acceptance condition — *nothing may keep calling the old name without anybody noticing it* — on the binary's help output, the README, the operator console, and MCP input schemas that freeze into every session at connect. Eight items below are text-or-wiring fixes with essentially zero behavioural risk; they belong in the tag, not after it.

I re-verified the load-bearing claims of every MUST-FIX item directly against HEAD (2801640) rather than trusting the dimension reports. Corrections to individual findings are noted inline.

## MUST FIX BEFORE THE TAG

**1. Live settings reach nothing on the only mounted endpoint** — `cmd/ken/main.go:412, 636, 643, 648, 668`
`/mcp` is `allserver.NewHTTPHandler`, built once with no rebuild path. `mcpHandler` and `stationHandler` are constructed and never passed to `mux.Handle` (v3.42.0 mounted both), yet both `live.OnChange` hooks still target them. `stationserver.NewHTTPHandler` takes `Deps` **by value** and installs `d.limits` on its own copy, so `stationDepsOut.limits` is nil and every `taskLim/noteLim/lockerLim/vaultLim` call falls back to the boot snapshot — measured: a 4 KiB `station_locker_put` succeeded against a handler whose cap had been lowered to 1 KiB. Curation-language edits likewise never reach `kb_save`'s frozen list entry (the `tooldoc.MustArrive` slot that exists precisely because a session cannot pull an answer it does not know to ask for). `settings.go:140/202` mark all thirteen fields `Live: true`, the console therefore suppresses its restart notice, and `OPERATION.md:177` states "there is no such thing as a restart-level setting". Two tests — `mcpserver/instructions_test.go:62 TestSetCurationLangsLive` and the station-limit path — are green against handlers no request can reach.
*Fix:* hand the live handles to `allserver` the way COMM already does (`commserver.RegisterTools` takes the `*Handler`), or, if you would rather defer, drop `Live: true` on those fields and correct §2.1 — but do not ship the current combination. Repoint both guarding tests at the served endpoint so they can fail. **Before tag.**

**2. Suspending a link produces the one refusal the wave says must never appear** — `internal/comm/pair_send.go:159-167`
`LinkMirrorRows` projects only `state='active'`, so a suspended pair vanishes from `station_link_mirror` entirely; `pair_send` then decides between `ErrUnknownStation` and `ErrNotLinked` by asking whether the target appears in *any* mirror row. When the peer holds no other active link — i.e. always in a two-station estate — the session is told "no station with that id is known here — check the id with comm_directory", and `comm_directory` returns that exact id. The session retries instead of telling its human, which is the single behaviour the SUSPENDED refusal exists to produce. The acceptance test at `internal/commserver/pair_send_http_test.go:437` is green only because the fixture also links `beta<->delta`; delete that unrelated `EnsureStationLink` and the shipped assertion fails with the wrong refusal.
*Fix:* in `commserver` (which already holds `d.Store`, so S7 is untouched), on `ErrUnknownStation` from a `to_station` send, ask ken.db whether that pair has a non-active link and swap in the suspended text. Rewrite the test so the suspend arm does not depend on a second station's link. **Before tag.**

**3. Two console controls report success for operations that did not happen** — `internal/web/comm.go:291, 348`; `internal/web/app.go:200-201`
*Revoke endpoint*: `RevokeEndpoint` only stamps `revoked_at`; `mailboxByStation` filters it out and `MailboxFor` recreates the mailbox on the station's next call. Nothing in `auth` consults `revoked_at` any more. The operator who clicks it to cut off a session gets a success flash and no effect — and its confirm dialog promises a binding voucher and a ROTATE control, both deleted. *Reassign mailbox*: route, handler, store function and form are all live, mutating `endpoint.session_key`, a column whose only remaining reader is the reassign function itself — while `COMM.md:873`, `UPGRADING.md:129` and `CHANGELOG.md:48` all state the form was deleted and `IDENTITY.md:186` tells the operator to use it.
*Fix:* delete the reassign route/handler/form (the docs already describe the world you want). For revoke, either delete the control or relabel it honestly as "reset this mailbox"; the real cut-off levers are archive-the-station and revoke-the-grant. **Before tag** — a security-shaped button that lies is worse than no button.

**4. The CLI advertises a deleted subcommand and teaches an inverted scope rule** — `cmd/ken/cli_station.go:24, 48, 125`; `cmd/ken/main.go:117, 164-176`
Verified at HEAD: `ken station add` **succeeds** and then prints `mint a key for a machine with: ken station key --station %s --label laptop`; both usage strings still read `add|list|rename|key|requests`, so `ken station key` dies with a usage line advertising the verb it just rejected — the retirement is rendered identically to a typo. `ken help` additionally says "/station needs a kens_ key BOUND to a station, which only ken station key mints", "a token may hold comm scopes or knowledge-base scopes, never both", and "neither may mix with knowledge-base scopes". `allserver.NewHTTPHandler` chains all three auth middlewares, so that rule is now *inverted*: an operator following help mints a credential `/mcp` refuses with 401. `CHANGELOG.md:44` and `UPGRADING.md:99` assert the subcommand is gone.
*Fix:* four string edits, plus an explicit `case "key": die("retired in 4.0.0 — see docs/UPGRADING.md")` so a scripted caller gets a distinguishable error. **Before tag.**

**5. README and AI-INTEGRATION.md hand new users credentials `/mcp` refuses** — `README.md:29-37, 100`; `docs/AI-INTEGRATION.md:19-38`
Measured on a running binary: `KEN_DEV_TOKEN=dev-secret` → 401 on `/mcp`; default `ken token add` scopes (`read,write-draft,propose`) → 401; `read,write-draft,propose,comm,station` → 200. The dev bypass lives only in `mcpserver/auth.go` and that handler is no longer mounted, so `KEN_DEV_TOKEN` now authenticates nothing anywhere — while `cmd/ken/main.go:233` still logs "the MCP endpoint accepts a static, unrevocable dev token" on every dev boot and `main.go:137` documents it in `--help`. AI-INTEGRATION §1/§2 are the public front door, and the three drop-in CLAUDE.md blocks repeat the wrong scope set, so human and model share the wrong premise.
*Fix:* correct both recipes to the full scope set (INSTALL.md:220 already has it), and decide `KEN_DEV_TOKEN`: give the bypass every capability or delete it and its two claims. **Before tag** — this is the first thing anyone does with a public MAJOR.

**6. Frozen MCP input-schema strings assert deleted gates** — `internal/commserver/types.go:486, 352, 354`; `internal/stationserver/types.go:157`
These cross the freeze: once a conversation opens against 4.0.0 they cannot be corrected by any deploy. `comm_open_channel.to_station` says "A human must already have approved a link between your station and that one"; `comm_file_offer.channel_id` says "the pairing-code channel to offer on" and `.to_station` "a station id an approved link joins you to"; `station_me.comm_endpoint_ids` says "If the endpoint_id in your credentials file is not in this list, you are using another session's credentials" — a credentials file this release abolished. Because `addTool` replaces `Description` with `tooldoc.Brief` (first sentence + pointer), the parameter schema is now the *only* substantive per-field text in the frozen tool object, with no adjacent sentence to contradict it. Note the sibling `comm_send.to_station` **was** correctly rewritten in this wave, so the sweep was targeted, not systematic.
*Fix:* four tag edits; delete `comm_endpoint_ids` outright (its documented purpose has no caller left). **Before tag,** because of the freeze.

**7. The /comm console still teaches the mechanisms this release deleted, in three locales** — `internal/i18n/locales/messages.properties:405, 417, 638, 628, 699` (+ es/fr)
Confirmed rendered strings. `comm.lede` (unconditional, `comm.html:6`): "A channel exists only because you created a pairing code — an agent cannot open one" — an *inverted* trust claim; in 4.0.0 an agent is the only thing that opens a channel. `comm.no_channels` (the fresh-install empty state): "Create a pairing code above" — there is nothing above. `comm.revoke_bound_endpoint_confirm`: promises a binding voucher and ROTATE. `flash.comm_released`: "Only its secret can drive it now, so rotate it". `rooms.deaf_lede`: tells the operator to have a session call `station_binding_voucher` then `comm_bind` — an instruction no session can perform. The wave deleted 18+ orphaned keys per locale but never re-read the surviving ones, which is exactly why an orphan sweep cannot catch this class.
*Fix:* ~6 keys × 3 locales. **Before tag.**

**8. Resume reports "Link ended"; suspending a dormant link reports success and does nothing** — `internal/web/stations.go:335-372`
`suspend := r.FormValue("resume") != "1"` is the only place the verb is distinguished; every exit path below it flashes revoke-era keys, so pressing **Resume** on the wave's headline reversible control renders "Link ended: dev / prod. No channels were open." in all three locales. Separately, `SetStationLinkSuspended` guards `WHERE state='active'`, and the handler swallows the resulting `ErrNotFound` on the written premise that it means "already in the target state" — a two-state argument applied to a three-state column, so suspending a **dormant** link (archived station) flashes success, changes nothing, and a later unarchive silently returns it to active.
*Fix:* new `station_link_resumed*` keys plus a branch on `suspend`; handle `ErrNotFound` per source state. Also drop the pointless `RevokeChannelsBetweenStations` on the resume path. **Before tag** (text + one branch).

## SHOULD FIX SOON (not tag-blocking)

- **`comm_file_offer{to_room|to_station, transfer:"upload"}` can never move a byte.** `GrantInfo.RecipientRow` is a plain `int64` and `ConsumeGrant` scans the NULLable `a.recipient_endpoint` into it; `CompleteUpload` thirty lines below scans the same column as `sql.NullInt64` with a comment naming this exact trap. Both upload and download 404 with nothing logged — the deliberate opacity renders a scan fault identically to "no such grant". Two-token fix + a test that actually consumes a room/pair grant. The error runs in the *safe* direction for confidentiality but the *dangerous* direction for durability: a reader concludes the snapshot is self-sufficient and never escrows the key, then a restore looks entirely successful with every secret unrecoverable. ## WHAT THE AUDIT DID NOT LOOK AT

Each of these is a gap in the evidence, not a clean result.

1. **~6,600 lines of deleted tests were never audited.** No dimension asked what those tests proved that nothing proves now. This is the largest hole in the whole audit and it sits directly under a release whose net is −6,200 lines.
2. **Nothing was exercised under a real OAuth grant.** Every wire test in every dimension used a hand-minted `ken_` token. The credential path a claude.ai connector actually uses — instructions, tool set, scope expansion, `MailboxFor` owner identity (`"oauth-<grantID>"`, shared by every station under one grant) — is unverified end to end. Related and unpursued: `commserver/files.go`'s `gi.EndpointToken != p.TokenID` check is *vacuous* under OAuth, leaving the grant string as the only thing separating one session's transfer from another's.
3. **Comm was never exercised over MCP against an upgraded comm.db.** The migration dimension verified the migrated database at schema and row level only; the auditor could not mint a full-capability token in time.
4. **The two rebuild migrations' data-moving paths have no automated coverage.** Every store test opens a fresh database, so `DELETE FROM station_request WHERE kind='link'` and 0026's `INSERT…SELECT` copy zero rows in every run. The in-place upgrade was one hand-seeded fixture, at zero production volume, from v24 only — no upgrade from <23, and no restore-then-upgrade of a real `ken backup snapshot`.
5. **The web session layer, CSRF, rate limiting and the whole `kb_*` authorization surface were audited by nobody.** The authorization dimension explicitly scoped them out and no other dimension picked them up.
6. **No `-race`, no `-count>1`, no mutation testing of the migration or web layers.** The `tooldoc` registry is a process-global shared across tests within a package; order-dependent masking was not probed. One structurally-real race remains unreproduced after 300 attempts: `commserver.syncLinkMirror` reads `LinkMirrorRows` from ken.db then calls `ReplaceLinkMirror` with no epoch guard (`_ = epoch`), so a pre-suspend snapshot could in principle land after a concurrent console suspend and re-authorise a suspended pair until the next console write.
7. **Nobody drove the console in a browser.** All console findings rest on route registrations plus template markup and, in several cases, handler-level HTTP tests — not on a rendered page.
8. **Locale coverage is one-directional.** The three bundles were confirmed to have identical key sets, but no dimension checked the es/fr *text* against current behaviour, and no dimension checked whether a `KEN_I18N_DIR` override could shadow the strings above.

---

**Bottom line:** the databases, the auth chain and the endpoint collapse are sound. Items 1–3 are real behaviour and are regressions of this wave; items 4–8 are text, and every one of them is the human's stated release condition failing on a surface a human or a session reads. Nine fixes, most of them string edits, and the tag is defensible. Ship the migration work with confidence; do not ship the help text.

## Slice 7 — should retiring the channel ship in 4.0.0?

# Why not retire the channel now (slice 7)?

## Recommendation

**Ship 4.0.0 as staged. Slice 7 becomes 5.0.0, scheduled with a date — not "Not scheduled."** But three things that the five reports found *while* scoping slice 7 are defects **today**, independent of the channel, and they belong in 4.0.0 or immediately after:

1. **`cumulativeAckScope` has no `p:` arm** (`internal/comm/message.go:846-859`). It resolves channel, then room, then refuses. Pairs — the addressing mode 4.0.0 makes primary — cannot be cumulatively acked at all. That is the exact regression `AckUpTo`'s own doc measured for rooms ("acking eight room messages took eight separate calls", `message.go:774-784`). ~4 lines plus a membership-not-existence test. It is not a slice-7 cost; slice 7 only makes it terminal.
2. **`comm_open_channel`'s first sentence is now its whole advertisement.** `tooldoc.Brief` takes `firstSentence` (`internal/tooldoc/tooldoc.go:118-133`) and `addTool` overwrites the wire description with it (`commserver.go:1144-1145`). What a frozen session sees is "*Open a named channel with another STATION.*" — the "*You will usually not need this*" that follows at `:406` is now behind a pull nobody has a reason to make. **The wave made the redundant tool more attractive than it was in 3.42.0.** Rewriting that opening sentence costs nothing, lands in the half of the surface that freezes at connect, and is the correct 4.0.0 move whether or not the tool is ever deleted.
3. **Four console strings name mechanisms this wave deleted**, live in all three locales: `comm.lede:405` ("*A channel exists only because you created a pairing code*"), `comm.no_channels:417` ("*Create a pairing code above*" — there is no form above), `comm.revoke_bound_endpoint_confirm:638` ("*a replacement session binds with a voucher*"), `rooms.deaf_lede:699` ("*Ask that session to call `station_binding_voucher` and then `comm_bind`*" — both tools gone from non-test Go). Plus `internal/web/comm.go:16-18` asserting "*an agent cannot create a channel, only redeem a code a human minted*" and `:88-91` promising voucher inheritance. **This is the human's condition failing inside 4.0.0 already, and it is fixable as prose without touching the table.** `TestConsoleTextDoesNotDescribeRemovedOrReplacedBehaviour` (`commserver_test.go:515`) does `if !strings.HasPrefix(line, "comm.optin") { continue }` — it inspects one key prefix, so it is green over all four. That gate needs widening more than the channel needs deleting.

Do those, and slice 7 in 5.0.0 becomes a pure deletion instead of a deletion bundled with three behavioural changes under audit pressure.

## What is actually lost

**One thing, and it is real: retroactive reach on the operator's brake.**

Three hand-mirrored predicates carry it — `LEFT JOIN channel c … AND (c.id IS NULL OR c.state='open')` in `PollScoped` (`message.go:489/493`), `queuedForEndpoint` (`:743/747`) and `pendingScopeSQL` (`pending.go:60/64`). A pair scope has **no such predicate**: `SendToStation` re-checks `areLinked` inside the writing transaction (`pair_send.go:151`), which stops the *next* send and nothing already queued. So suspending a link today is retroactive for channel traffic and prospective for pair traffic, and `handleStationLinkSuspend` papers over the split by sweeping channels (`web/stations.go:356`). Delete the channel and suspension is prospective everywhere, while `stations.link_suspend_help:643` still says "*Live channels close*" and `stations.link_suspend_confirm:644` still says "*This closes {2} live channel(s)*" — which would render `0` for a relationship with mail in flight. Zero-because-nothing-is-in-flight and zero-because-this-counter-cannot-see-pairs are byte-identical: the project's named defect class, in the one dialog whose job is to price a destructive action.

**Does it matter to this deployment?** Marginally, in practice: one operator, sessions he controls, and the exposure is bounded by `comm_undelivered_ttl_sec`. It matters as a *statement*: either the suspend path grows a "expire queued `p:` deliveries" sweep and gates `GrantDownload` on `areLinked` for pair scopes (`file.go:561-571` — its comment justifies the missing check with "*the membership check above already asked the live roster*", true for a room's `room_member_mirror`, false for a pair whose roster is an immutable scope string), or the confirm text is rewritten to say what suspension actually does. Slice 7 must pick one **explicitly**; deleting `revoke_retroactive_test.go` "because the mechanism went" is how the property disappears without a decision.

**Everything else is not a loss.** A durable id to address a long exchange by: the pair scope is `p:<a>|<b>`, derived from two ids in the durable database, returned by `comm_channels.Pairs` "never omitempty, never nil" (`types.go:62-67`) and echoed as `reply_to_station` on every inbound message. Ordering and sequence: allocated per **scope** by `nextScopeSeq` for both writers since migration 0009 — identical guarantee. Backpressure: the same `MaxUnackedPerChannel` over `m.scope_id` in both paths (`message.go:213`, `room_send.go:183`) — and a pair that *also* holds a channel silently gets **two** 64-deep budgets for one relationship, so deletion makes the setting mean its label. Labels: `channel.label` is not in `channelView`, so no session can ever read it; on reuse the supplied label is discarded. Successor inheritance: the pair needs no `station_a/station_b` snapshot columns because membership *is* the scope string.

And the channel is **strictly weaker on reachability**: `comm_open_channel` requires `LiveEndpointForStation` (`channel.go:548-561`), which returns `ErrNotFound` when nobody is staffing the peer; `comm_send{to_station}` mints the mailbox get-or-create and needs no one home. A channel also cannot be first contact — the only `INSERT INTO station_link` is `EnsureStationLink`, reached only from `comm_send{to_station}` — so by construction it is never anyone's first move, and `OpenLinkedChannel` reuses per station pair (`:435-447`), so it is one-per-relationship: exactly what the pair scope is.

## Migration shape — the reports disagree, and two of them are wrong

The code-inventory and blast-radius reports both say the column drops force SQLite table rebuilds, and the blast-radius report says `idx_message_seq ON message(channel_id, sender_endpoint, seq)` must be dropped first. **That index has not existed since migration 0009**: it is created only at `0001_init.sql:186`, and `0009_delivery.sql:126` does `DROP TABLE message` and recreates it with four new indexes, none on `channel_id`. Verified — no index anywhere in `migrations/*.sql` references `message.channel_id`. So `ALTER TABLE message DROP COLUMN channel_id` runs in place, as the data-and-migration report measured against a v20 database at the pinned driver (≥ 3.53, floor already pinned by `sqlite_floor_test.go:26`).

The one blocker is `idx_attachment_idem` (`0002_files.sql:63-65`), still keyed on `(channel_id, sender_endpoint, idempotency_key)` while the lookup has been keyed on `scope_id` since 0017 (`file.go:352`). It must be dropped before the column can go — **and it must be rebuilt scope-shaped with a de-dup pass first**, because SQLite treats NULLs as distinct, so file-offer idempotency is currently **unenforced at the storage layer for every room/pair offer**, and building the correct index over existing duplicates aborts. That is a live defect owed regardless of slice 7.

The other adjudication: **"comm.db may start empty" does not make the migration free, and it does not make 4.0.0 the only free window.** The empty-start ruling is scoped to *this* upgrade (`docs/UPGRADING.md:53-62`); 4.0.0 still ships `comm_open_channel`, so channels accumulate again immediately. The correct migration does not delete rows anyway — it *settles* them (mark deliveries `expired`, push `expires_at` into the past, hand attachments to the sweep that unlinks bytes before deleting rows) — and that works identically on a populated database. The extra cost of deferring is roughly ten lines of SQL and one populated fixture test, not a `0017`-shaped rewrite. The release-strategy report's headline reason ("*the only release in which the schema half is free*") does not survive that.

Two traps that must survive into whenever it ships, both measured: `dbmigrate.Run` disables foreign keys for the whole run (`dbmigrate.go:79`), so a naive `DELETE FROM message` does **not** cascade and leaves dangling `delivery`/`transfer_grant` rows that `dbmigrate.go:110-115` turns into a hard upgrade failure; and deleting `attachment` rows orphans bytes forever, because the row is the only record of which file to unlink (`file.go:849-851`) and the only directory scan handles `.part` files.

Also on the historical-migration tests: the code-inventory report says all four must pass unchanged; the blast-radius report says `migration_0017_upgrade_test.go` dies. Both half-right. The hand-built historical SQL inside those tests never changes; but `0017_upgrade_test.go:74` asserts on `att.ChannelID`, a Go field that would be deleted, and `migration_0017_test.go:40` asserts the shipped schema still carries `REFERENCES channel(id) ON DELETE CASCADE`. The first needs an edit, the second breaks loudly and correctly.

## G1. The per-token rate limit is charged THREE times per request on the only endpoint that exists — every session's effective limit is one third of what the setting, the log line and the docs say

**No dimension exercised the endpoint under load or with a limiter configured.** This is a live-behaviour regression of the wave.

`cmd/ken/main.go:263` builds one `rlToken`; `:368`, `:505` and `:603` hand **the same instance** to `mcpserver.Deps`, `commserver.Deps` and `stationserver.Deps`. `allserver.go:129-133` chains all three `AuthMiddleware`s on `/mcp`, and each one calls `limiter.Allow(p.TokenID)` on the same token id — `mcpserver/auth.go:104`, `commserver/auth.go:117`, `stationserver/auth.go:224`.

Measured on real binaries, `KEN_RATELIMIT_TOKEN_RPM=60 KEN_RATELIMIT_TOKEN_BURST=6`, ten rapid `initialize` POSTs with a full-capability `ken_` token:

| binary / path | result |
|---|---|
| **HEAD `/mcp`** | `200 200 429 429 429 429 429 429 429 429` |
| v3.42.0 `/mcp` (one chain — control) | `200 200 200 200 200 200 429 429 429 429` |
| v3.42.0 `/all/mcp` (three chains — control) | `200 200 429 429 429 429 429 429 429 429` |

Six tokens buy two requests. The shipped default `120/min, burst 60` is really **40/min, burst 20**. The boot log prints `per-token 120/min (burst 60)`, `settings.field.rl_token_rpm.label` says "Per-token requests / minute", and `commserver.go:54` states "TokenLimiter is comm's own rate bucket, separate from the knowledge base's" — all three now overstate by 3×. The defect existed in 3.42.0's opt-in `/all/mcp`; the wave made it the only surface.

**Same cause, second effect:** `commserver/auth.go:130` and `stationserver/auth.go:243` call `st.TouchToken` **unthrottled**, so every `/mcp` request now issues two extra `UPDATE api_token` statements on the single writer connection. `mcpserver/auth.go:145-148` documents that its throttle exists specifically to "avoid acquiring the single-writer connection needlessly" — that purpose is now defeated on every request. `stationserver/auth.go:239-241` claims its touch is "throttled to about once a minute"; the throttle is the SQL time-guard in `store/tokens.go:288-290`, not the call, so the statement is issued regardless.

*Fix:* charge the bucket once per request (limit in one place in `allserver`, pass nil limiters to the inner two, or mark the request context as already-limited).

## G2. The documented ROLLBACK path is silently broken by this release, and nobody looked at the downgrade direction at all

Eight dimensions all ran the upgrade forward. `docs/INSTALL.md:328-334` says *"Roll back by pointing `current` at a previous release and restarting"* with `data/` "preserved untouched", and `docs/REMOTE-UPGRADE.md:45` lists `--version X.Y.Z` as *"install/rollback to a specific published version"*.

## G3. `/comm/files` authorises a transfer against a column that any other session on the station rewrites — and the grant is burnt before the check runs

`internal/commserver/files.go` was **not touched by this wave** (only `files_test.go` changed). The authorization dimension explicitly excluded the relay; the new-code dimension read `MailboxFor` but not its consumers. So the collision between "a mailbox belongs to a station, not a session" and an unchanged relay was audited by nobody.

- `internal/comm/file.go:670-675` — `ConsumeGrant` reads `GrantInfo.EndpointToken` **live** from `JOIN endpoint e … SELECT e.token_id`.
- `internal/comm/endpoint.go:426-433` — `MailboxFor` **rewrites** `endpoint.token_id` to whichever credential called last, on every comm call.
- `internal/commserver/files.go:91` / `:192` — `if gi.EndpointToken != p.TokenID { 403 }`.

Proven at store level (`go test` in the scratchpad copy):

```
CONTROL              EndpointToken="tok-A"           (offering session)
AFTER 2nd CREDENTIAL EndpointToken="tok-SUCCESSOR"   (grant was minted under tok-A)
```

So after any second credential touches that station's mailbox, the offering session's own `PUT /comm/files/<grant>` returns `403 grant does not belong to this token` — and `ConsumeGrant` has already stamped `consumed_at` (`file.go:665-667`), so the single-use grant is spent and the 403 is logged nowhere. The symmetric half is worse: a credential that has *since* claimed the mailbox can consume a grant it never minted. `files.go:26-31` still states the invariant as "the bearer … must OWN the endpoint the grant was minted for"; ownership is now time-varying and mutable by a third party. (Under OAuth every session shares one `TokenID`, which hides the false refusal — and is the same fact that makes the check vacuous, already in the verdict. Under `ken_` tokens, which is how the operator's machines authenticate, it bites.)

*Fix:* snapshot the minting token onto `transfer_grant` at offer time and compare against that, or authorise the relay by resolved station rather than by token id.
