## 1. The posture, in one line

**All Ken services, in all sessions, with as little friction as possible.**

## 2. Identity and registration — settled requirements

- **OAuth through claude.ai is THE mechanism.** Not one of several. *"It should be the only
  mechanism available to all future users."*
- **One registration (in claude.ai) per Ken user.**
- **One Ken user — one human — per Ken instance.**
- **One Claude account per Ken instance.**

## 3. What the human is willing to approve, and what they are not

**Willing** — and explicitly, because control and revocation depend on it:

| approval | how often |
|---|---|
| a **device** | once |
| a **session** | once — *"but only one!"* |
| a **Comm channel** | once per end, on first usage |

**Not willing, at all:** *"no keys, tokens or other codes generated by the human."*

That last line is the requirement most of the current design violates, and it is the one that
broke the station handover on 2026-08-18: the human was told to move a credential from a browser
into a config file by hand, through a channel the same instruction prohibited.

## 4. The flow he wants

1. Install the Claude client on a device, or open claude.ai in a browser, and **log in**.
2. **From that moment Ken is available on that device** to the sessions that live there.
   *This already happens for the knowledge base. It should also be true for Comm and Station.*
3. Only Claude Code sessions can use Comm and Station.
4. **On a session's first use of Comm or Station, the KEN SERVER creates a unique id** for that
   session, which identifies it permanently until the session ceases to exist.
5. **On a session first joining a channel, the KEN SERVER generates a unique id for the channel**,
   and the session requests access to it.
6. **The session creates the channel, prompted by the human in words** — e.g. *"You need to
   communicate with session (or station) XXX over Ken."*
7. **The human approves in the Ken console, and SEES the channel id there.**
8. The human goes to the other end and prompts: *"Join the Ken channel with ID YYYYYY."*

**Net: one approval per device, one per session, one per channel end — and no human-generated
secrets anywhere in it.**

## 5. How far today's design is from that

Recorded as fact, not as a verdict on what to do about it.

| requirement | today |
|---|---|
| OAuth is the only mechanism | OAuth covers `/mcp` only. `/comm/mcp` refuses non-`ken_` credentials by design; `/station/mcp` accepts only `kens_` keys. Both structurally require a long-lived static bearer in client config, with **no expiry** — `api_token` has `revoked_at` and `retired_at` and no `expires_at`. |
| available on the device after login | true for the knowledge base; **not** for Comm or Station, both of which need a credential placed in client config by hand |
| server generates the session id | the session registers an endpoint and receives a **secret it must store itself**, in a `0600` file, and re-read after every context compaction |
| server generates the channel id | Ken generates the channel id — but reaching it needs a **human-minted pairing code**, or a link the human approves and a session then spends |
| human sees the channel id to relay | the human mints and relays a **pairing code**, not a channel id |
| no human-generated keys or codes | pairing codes, station keys and comm tokens are all human-generated today |

**One thing already matches**: the human approving a link, and a channel resulting from that
approval, is exactly the shape of step 7 — and since 3.11.0 the approval names both stations and
opens the conversation itself.

## 6. The tension this creates with work already agreed

**Stated so it is visible, NOT acted on.** Batch 6 was derived from Batch 5's decisions, which
were made before this. Three of its items now point somewhere Vlad has said he does not want to
go:

- **D — "station key authenticates `/comm/mcp`"** is a *second static credential* model. It is the
  opposite direction from OAuth-only, and its stated precondition — *every session holds a
  station* — stopped being true when Station was dropped.
- **The endpoint migration** binds endpoints to stations on an estate whose owner has stopped
  using stations.
- **P2 — `comm_send{to_station}`** is addressing between stations, which survives the concern but
  inherits its container from it.

**These are not decisions to take here.** They are the first things the post-finishing analysis
has to resolve, and they are recorded now precisely so that finishing does not quietly build the
wrong thing on the way past.

## 7. Observed problems this destination would have to solve

Everything below was *found*, not proposed. Each is already recorded in its own place; this is
the index, so that the analysis starts from evidence.

**Provisioning is where it actually breaks.**

- The handover instruction was **self-contradictory**: the key must never enter a prompt, and the
  only delivery path offered was to hand it to a session through a prompt. The key was burned on
  arrival, and the session's own attempted redaction leaked a second credential in the same
  breath. *(2026-08-18, ken-prod-ops owns the instruction.)*
- **The remedy Ken prints for an actor mismatch cannot work.** Both the operator and the session
  are told a key must be re-minted from the console — and the console mints under the logged-in
  human while its comm-token path is hardcoded to `kind='ai'`, with `(kind, display_name)` unique.
  The two console mint paths sit on opposite sides of a partition and cannot meet. Confirmed in
  production 2026-08-18: the first console-minted station key ever created carries actor
  `human:admin`.
- **The console diagnoses the problem and cannot fix it.** A `no COMM token` badge renders with
  help text saying "mint a key under the actor that holds this machine's COMM token", on a form
  whose only field is `label`. Verified by eye on the live console.
- **A human-actor station key silently breaks the hearsay marker** — `prompted_by_peer_traffic`
  becomes permanently false, with nothing said on either side.
- **A wrong actor can produce a successful-looking bind into the wrong station.** The actor check
  is not a same-station check, and "the actor matches" reads like "this is the right station".

**Credentials and their lifecycle.**

- The endpoint pair travelled as **tool arguments** into client transcripts until 3.11.0; the
  headers are in, the arguments remain for compatibility.
- **`api_token` has no expiry** — only revocation and retirement.
- **Ken cannot answer "was this credential used by someone else."** No column in either database
  records a request source address; `last_used_at` gives when, never where. Unanswerable is not
  the same as no.
- **A live credential may not appear in the table an operator would search** — an app-scoped
  OAuth registration is invisible to a query over `api_token`, so that query returns the same
  empty result whether access exists or not.
- **Console-vs-CLI provenance is not auditable**: `api_token` has no origin column.
- **Open and being traced by ken-prod-ops**: does revoking a comm token orphan the endpoints
  registered under it?

**Things that failed silently, and cost real work.**

- The idle sweep collected an endpoint holding a channel seat and **cascaded the channel away**,
  with no log line. Fixed in 3.8.0 — after it had already destroyed a live channel twice on a
  machine nobody was watching, each repair costing a human-minted pairing code.
- A **station's messaging identity and its station identity can be entirely unjoined** —
  `quest-infra` wrote 47 tasks under one and received 83 deliveries under the other, with zero to
  its station party, for three weeks. Nothing reports it.
- **`expired` does not distinguish "delivery fault" from "recipient never polled."** The rows are
  identical. The fix needs nothing stored: compare the recipient's `last_seen_at` against the
  delivery's `expires_at` at notice time. *"Expired" is an observation; "recipient absent since X"
  is an instruction.*
- **The set of sessions is never closed.** An endpoint was created two minutes before an operator
  read the table. Anything premised on "every session holds a station" must handle a session that
  registers mid-flight.

**Text that described controls Ken did not have** — the class that propagates fastest, and the one
this project has paid for most often. Collected in `FINISHING.md`; the pattern is the point.
